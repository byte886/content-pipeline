# 批量任务执行规范（BATCH_TASK_EXECUTION）

> **文档类型**：Standard（规范 — 批量任务执行）
> **维护者**：AI自动维护

---

## 1. 什么时候需要创建状态记录

满足任一条件即必须创建：
1. 批量处理 >3 个项目
2. 预计执行时间 >1 小时
3. 涉及多个工具链

---

## 2. 状态记录落点

| 层级 | 位置 | 内容 |
|------|------|------|
| 批次明细 | `workspace/capture/state/` | 具体进度、断点、锁文件（不入库） |
| 指针级状态 | `active/TASK_STATUS.md` | 只更新工单状态，不抄批次明细 |

**原则**：TASK_STATUS.md 是进度真相，但只放指针，不放批次明细。

---

## 3. 状态记录格式

### 3.1 批次状态文件（JSON）

```json
{
  "batch_id": "capture_20260915_001",
  "status": "running|completed|failed",
  "total": 313,
  "completed": 150,
  "failed": 2,
  "current_item": "短视频_150_xxx.mp4",
  "failed_items": [{"name": "xxx.mp4", "reason": "下载超时"}]
}
```

### 3.2 锁文件

- 位置：`workspace/capture/state/<task_type>.lock`
- 作用：防止多进程冲突
- 任务完成后必须删除

---

## 4. 异常恢复流程

1. 检查锁文件 → PID不存在但锁文件存在 → 异常中断
2. 读取批次状态文件 → 跳过已完成项 → 重试失败项（最多3次）

**紧急恢复**（全网阻断）：见 AGENTS.md §2.1

---

## 5. 必须立即更新TASK_STATUS.md的场景

1. 任务开始/完成时
2. 遇到问题或阻塞时
3. 每次git提交前

---

## 6. 性能与资源保护

1. 单次批次不超过 500 个项目（超过则分批）
2. 下载并发数不超过 5（避免触发风控）
3. 转写单进程运行（FunASR占用资源大）
4. 每处理 50 个项目保存一次状态
5. 失败项最多重试 3 次

---

## 7. 完成标准

- [ ] 所有项目都已处理（总数 = 已完成 + 已跳过）
- [ ] 失败项有明确原因记录
- [ ] 状态文件已更新为"完成"，锁文件已删除
- [ ] TASK_STATUS.md 已更新
- [ ] 按 DOC_SYNC_CHECKLIST.md 同步相关文档
