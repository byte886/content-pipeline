## 1. 执行摘要

**现状一句话**：采集主干端到端已跑通（七平台下载 → 字幕 / FunASR 转写 → 画面 OCR / 智能抽帧，郭颖 387 台账 → 322 下载 → 323 转写、视频号全量闭环），知识化与质检已有 OKF v0.2 校验器 + 吸收对账 + 近重复普查 + A/B/C 分级工单流转，云文档组织守则与「鉴藏知识库·孵化」容器已落地（来源：技能 SKILL.md、content-pipeline WORKFLOW.md、郭颖目录、云文档守则）。

**目标一句话**：把散落的技能 / SOP / 产物串成一条可编排的主流程——**采集前预判（G0，含素材类型分路）→ 多模态采集（视频 / 音频 / PDF / 图片 / 文本 / 线上图文）+ 评论 + 字幕 → 多模态提取（转写 / OCR / PDF 解析 / 图文解析）→ 按行业需要做视频 / 多媒体分析 → 最终文稿 → OKF 知识库（跨模态归并）→ 检查迭代 → 云文档发布与维护**。素材类型不限视频（2026-10-12 用户拍板新增硬需求，详见 §4.1 G0、§5.4）。

**三大真缺口**（调研证据，详见 §3.5）：
1. **评论采集未成正式环节**：仅小红书有专用脚本（≤3 页风控），抖音靠人工临时翻屏，B 站 / 视频号只取计数，YouTube / 腾讯 / 直播无；未接入主流水线。
2. **文稿 → OKF 无融合桥**：`library/06_articles` 已有 298 篇文章，但 `type: ArticleNote` 产物为 0 篇；视频链路 SOP 完备，文章链路是断的。
3. **质检闭环缺"持续复审 + 人工复核"环**：机械门（okf_validate / doc_health / 双维查重）已可执行，但语义一致性自检、frontmatter 与正文一致性、`verified: human:` 人工复核在郭颖 23 篇全部缺位；行情类内容无 `stale_after`。

**路径**：P0 规划落盘 ✅ → P1 统一工作流骨架（含多模态路由）✅ → P2 评论采集 + 多模态采集接入 → P3 文稿↔知识库融合桥 → P4 质检加固 → P5 视频分析行业矩阵 → P6 云文档维护机制 → P7 多智能体编排试点 → P8 手机端 / 小程序形态研究（详见 §10，可分批执行、每批可验收）。

## 4. 目标工作流设计（端到端）

### 4.0 阶段总览

```
S0 任务定义与预判(采集前) ──G0──> S1 采集(下载+评论+字幕) ──G1/G2──> S2 内容提取(转写/OCR/翻译)
      │                                                                      │
      │G0 决定:形态/行业/是否需要OCR/视频分析/评论/范围                          └──G3──> S3 视频分析(按行业)
      v                                                                                 │
S7 云文档发布与维护 <──G6── S6 质检与迭代 <──G5── S5 知识化(OKF) <──G4── S4 最终文稿合成
      (残留/过时/毕业/索引)   (机械门+人工复核+评估Agent)  (归并/新建)     (字幕+转写+OCR+评论+视频分析融合)
```

- **S0–S1 即用户所说"视频采集前的预判"落点**：先判形态与策略，再动手采集。
- **S2–S4 即"根据字幕或音频转文稿，按预判做 OCR / 视频分析，完成最终文稿"**。
- **S5–S6 即"按郭颖那样的过程转化成不同 OKF 知识库，检查迭代直到完成"**。
- **S7 即"按云文档组织要求和文档写作要求放到云文档"** + 残留 / 过时处理。
- **多模态扩展（2026-10-12 用户拍板新增）**：素材类型不限视频——音频 / PDF / 图片 / 文本 / 线上图文（小红书图文、公众号文章）各走各自采集与提取路径（§5.4 路由表），G0 按素材类型分路，知识化阶段跨模态归并（§6.2）。

### 4.1 决策门定义（G0–G6）

| 门 | 名称 | 输入 | 规则（来源） | 输出 |
|---|---|---|---|---|
| **G0** | 采集前预判 | 用户需求（博主 / 链接 / 主题 / 行业 / 素材） | ① 目标形态：出文稿？建知识库？视频分析？评论研究？组合（§6.2 双写）；② 行业识别 → 选 domain-plugin（jewelry / video-creation / 新增）；③ 内容路线预判：字幕 / 音频 / OCR 是否需要（§3.3 六条默认行为）；④ 视频分析是否需要（判型表）；⑤ 评论是否需要；⑥ 范围：单条 / 批量 / 全量 / 增量；⑦ **素材类型分路**：视频 / 音频 / PDF / 图片 / 文本 / 线上图文，各走各自提取路径（转写 / OCR / PDF 解析 / 图文解析），见 §5.4 路由表；⑧ 跨模态归并预判：同主题多模态素材是否合并建条目（§6.2） | **任务卡**（manifest：目标形态 / **素材类型** / 行业 / 路线 / 平台 / 批次 / 状态） |
| **G1** | 字幕探测后选路 | 平台字幕探测结果 | SKILL.md 六条默认行为：有字幕只下字幕；无→最小音频；无音轨→可 OCR 视频（≤720p） | route = subtitle / audio / video-for-ocr，写入 fetch-manifest |
| **G2** | OCR 决策 | 预判 + 兜底 | 预判需要画面文字（对比 / 图表 / 界面 / 珠宝实物细节）或兜底（视频实际无声、新片静音流 -91dB → 硬字幕 OCR） | 是否跑 macos_vision_ocr_pipeline + 抽帧 |

## 6. 知识化与 OKF（含融合桥设计）

### 6.1 OKF v0.2 与双形态对照

- **规范内核**（来源：okf-wiki/reference/OKF-SPEC-v0.2.md + scripts/okf_validate.py 逐行实判）：包结构 = index.md（导航，根 index 唯一可带 okf_version）/ log.md（倒序变更，禁 frontmatter）/ PROJECT-AGENTS（schema）/ concepts/*.md（一文件一知识点）/ references/（外部材料镜像）；**唯一硬必填 frontmatter 字段是 `type`**；E1（非 `---` 开头 / 无闭合）/ E2（空 type）/ E3（子目录 index 带 frontmatter、log.md 带 frontmatter）；W10–W81（缺 title/description、timestamp 遗留、status 非法、时间非 ISO8601、stale_after 到期、sources 缺 resource、脚注对不上、index 无条目、log 日期格式、死链、孤儿页等）；退出码：有 E → 1，`--strict` 有 W → 1。
- **郭颖形态①**（23 篇）：`type: Knowledge`、sources 仅 resource（抖音 URL）+ title（**无 id / author / last_modified**）、`status: stable`、generated 标记；**无 verified、无 stale_after**；正文用 `〔转写〕〔观点〕〔OCR〕〔批X补采〕` 标注。
- **老许形态②**（744 篇 draft）：`type: VideoNote`、sources 带 id（src-bili / src-transcript）+ 本地转写路径 + `author: human:`、`[^BV]` 强制脚注。
- 设计缺口：形态①用 `type: Knowledge` 不在 design 词表内（**待核**是否有意另立词表，§12-④）；两种形态并存需统一词表策略（P3 解决）。

### 6.2 文稿 → OKF 融合桥（缺口②，P3 实施）

**问题**：`library/06_articles` 已有 298 篇文章，但 `grep type: ArticleNote` = 0 篇——文章链路与知识链路完全平行，不互通。

**桥设计（"同一躯干，成文层双写"）**：
1. **共用躯干只跑一次**：下载 → 转写 → OCR / 抽帧（S1–S2）为唯一真相；
2. **成文层双写**：S4 出读者文稿（article，06_articles）+ S5 出知识条目（knowledge note，05_knowledge，`type: ArticleNote` 或按 G5 归并进已有知识文档）；
3. **链接协议**：manifest 同一条记录写两个 `artifact` 指针（article 路径 ↔ 知识文档路径），两产物互相可见、可追溯同一来源视频；
4. **落地物**：`docs/workflow/article-to-okf-bridge.md`（SOP：何时双写、如何归并、ArticleNote frontmatter 模板、与郭颖形态①的关系）。
5. **跨模态归并（2026-10-12 新增）**：同主题下，视频知识条目 + 音频精华 + PDF 章节 + 图文要点 + 文章观点**合并进同一知识文档**；各模态来源分别标注（如 `src-douyin` / `src-pdf` / `src-xhs` / `src-article`），frontmatter `sources` 可含多模态条目；归并触发由 G5 判定（§6.3 增量归并规则扩展）。

### 6.3 增量归并规则

- 成文原则：**并入已有知识文档为主，确属新主题才新建**（郭颖 145 科普 → 14 品类、46 实战 → 3 手册；跨博主老许只写增量、不抄郭颖）。

## 8. 云文档维护机制

### 8.1 发布流程（S7 执行序）

1. 本地知识库过 S6 质量门 → 按守则决策树判定落点（云盘孵化 or Wiki）；
2. 放置对应项目 / 模块文件夹（先读内容再归类、成套不拆散、优先复用现有文件夹）；
3. **新增重要文档补 00_索引**（守则·四.5）；
4. 记录本次发布（云文档维护记录，本地 workspace 一份）。

### 8.2 残留 / 过时 / 重复检测与处理

| 检测项 | 方法 | 处理 | 依据 |
|---|---|---|---|
| 残留（本地已更新/毕业，云盘旧版空壳） | 定期对账：本地 library ↔ 云盘孵化 ↔ Wiki，比对文档清单与日期 | 标「待清理」→ 用户确认后删除 / 归位；毕业迁移后清理空壳 | 守则·六；风险 R1 |
| 过时（内容已更新，云文档未同步） | 对账时比对本地 README 更新时间 vs 云文档；**旧版标退役**：`[已退役 日期：原因]` | 更新云文档；退役标注范式 | pipeline §2.6 退役范式；风险 R3 |
| 重复（同义文件夹 / 文档 / 多版本） | 标题 / 链接 / 内容指纹去重；新文档写入前 grep 现有目录 | 合并或删除（用户确认）；不新建同义文件夹 | 守则·四.3、五；风险 R4 |
| 数字口径漂移 | 统一计数口径（如郭颖"23 份 = 14 品类 + 3 手册 + 6 早期"写入云盘索引旁注） | 索引注明口径 | 风险 R6（已闭环） |
| 三处不一致 | **以本地为权威源**：出入以本地 OKF 文档 + 原始视频为准 | 云文档向本地对齐 | 用户决定；风险 R5 |

**权威源约定**（用户已确认）：本地仓库 = 权威源，云文档 = 展示 / 协作层；每层要 README；组织方法文档给后续 AI。

### 8.3 毕业机制与索引同步

- 毕业：云盘内容真正成型、结构稳定、长期复用 → **向用户提议**迁入 Wiki；迁移前**必须用户确认**；迁移后清理空壳并更新总导航与索引（守则·六）。
- 索引同步：每个项目 00_索引维护责任在发布 Agent（S7）；新增重要文档后**顺手补链接**（守则·四.5）。
- 知识库新建：新建知识空间 / 新顶层文件夹必须先问用户（守则·四.4）。

## 9. 多智能体协作设计

### 9.1 角色表

| 角色 | 职责 | 输入 → 输出 | 依赖 |
|---|---|---|---|
| 编排 Agent（OrganizeAgent） | 按 S0–S7 调度、切分任务卡、验收整合 | 任务卡 → 阶段产物汇总 | 全部 |
| 采集 Agent | 平台适配层执行（下载 / 字幕 / **评论**）、风控纪律 | 任务卡 → 原始文件 + 评论导出 + 清单更新 | 平台策略 |
| 处理 Agent | 转写 / OCR / 抽帧 / 翻译 | 音视频 → transcript / ocr / 关键帧 | 脚本 |
| 视频分析 Agent | 判型命中后按行业做画面层 + 音频层分析 | 视频 → 分析报告（路由 video-studio / OKF） | 行业插件矩阵 |
| 成文 Agent | 多源融合出最终文稿（7 类角色结构） | 素材 → article | 评论信号、分析报告 |
| 知识化 Agent | OKF 生成 / G5 归并 / frontmatter 回填 / 对账 | 文稿 / 素材 → OKF bundle | okf-wiki |
| 质检 Agent | 机械门全跑 + 对账 + 查重 | 产物 → 质检报告 | 脚本 |
| **评估 Agent（独立）** | 复查覆盖性 / 忠实性 / 行业准确性；上下文与生产 Agent **隔离** | 质检后产物 → 复查结论 | 来源库 |
| 云文档 Agent | S7 发布 / 索引 / 残留检测 / 毕业提议 | OKF stable → 云文档更新 | 守则 |

### 9.2 编排与衔接协议

- **衔接载体 = 任务卡 / manifest 状态机**：扩展郭颖 manifest.csv 16 列状态机，新增 `route / comment_done / analysis_done / article_path / knowledge_path / qc_status / cloud_status` 列；每阶段只写自己负责列，下游只读已完成列。
- **并行规则**：同阶段多视频切片并行（抖音批次 ≤15 条、≥30s/条风控纪律）；跨阶段严格串行（S6 质检依赖 S5 产物）。
- **独立验证**：评估 Agent 单独派发、隔离上下文，不与被评 Agent 共享会话。
- **人类介入点**：登录 / 验证码 / 人工开窗（微信视频号）、云文档删除 / 迁移 / 新建空间 / 毕业确认（守则要求用户确认的操作）。

### 9.3 与现有能力的差异

现有 content-pipeline 为脚本 + 单人 AI 执行；目标态为"编排 Agent + 专业角色 Agent + 独立评估 Agent"的多人协作，但**底层脚本与技能全部复用**，不重写。P7 以小批量端到端试点验证衔接协议后再推广。
