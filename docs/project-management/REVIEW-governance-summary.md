## 二、项目治理体系

### 2.1 治理体系来源

项目治理体系**深度参考了高顿CPA课程知识库项目**（gaodun-course-knowledge-base）的成熟架构，结合本项目特点进行了适配。

高顿项目的核心治理理念：
- **文档是项目的"集体记忆"**，必须依赖文档而非对话记忆
- **问题驱动更新**：发现问题立即评估是否需要更新文档
- **变更影响分级**：L0顺手修复 / L1高扩散变更（先方案后执行）/ L2架构变更（先讨论后执行）
- **冷启动/续接双路径**：新会话按路径读文档恢复上下文，不依赖对话记忆

### 2.2 文档架构

```
docs/
├── README.md                    # 项目概览（给人看）
├── AGENTS.md                    # AI操作手册（命令式、可执行）
├── REQUIREMENTS.md              # 需求与决策溯源（合并了PRD）
├── DIRECTORY_STRUCTURE.md       # 目录结构与存储分工
├── DOCUMENTATION_MAP.md         # 文档地图（按场景快速入口）
├── WORKFLOW.md                  # 整体工作流（四阶段流水线+校验门）
├── ROADMAP.md                   # 项目路线图
├── DESIGN-knowledge-base-organization.md             # 知识库架构设计（合并了知识库规范）
├── SOP-wechat-channels-capture.md          # 平台级SOP
├── SOP-wechat-official-article.md          # 平台级SOP
├── RESEARCH-video-quality-url.md              # 技术研究记录
```

### 2.3 核心治理机制

#### 2.3.1 问题驱动更新（强制）

发现任何问题（文件位置不对、脚本有bug、流程有缺陷、文档缺失等）时：
1. 立即评估是否需要更新文档或自动化检查
2. 评估后必须执行，不能只发现问题不更新
3. 记录到任务报告或ISSUES.md

#### 2.3.2 变更影响分级（强制：先确认再执行）

| 级别 | 定义 | 处理方式 |
|------|------|----------|
| **L0 顺手修复** | 错字、单处断链、单文件明显小错 | 直接修复并记录 |
| **L1 高扩散变更** | 批量重命名/跨目录移动、≥5处引用级联、修改治理规范本身 | **先出方案+全量影响清单，用户确认后才执行**；本地改完先不push，验收后提交 |
| **L2 架构/流程变更** | 流程变更、架构调整、新增功能 | 先和用户讨论，确认方案后再执行 |

> 拿不准属于哪一级时，**就高不就低**，先按L1出方案。

#### 2.3.3 冷启动/续接双路径

**路径A · 冷启动**（首次接触/跨阶段切换/对任务归属没把握）：
1. 读README.md — 项目概览
2. 读工程记忆memory/index.md — 稳定结论定位
3. 读REQUIREMENTS.md — 项目目标与验收标准
4. 读WORKFLOW.md对应环节 — 沿链接读专项SOP
5. 读TASK_STATUS.md + ISSUES.md — 当前状态

**路径B · 续接**（用户说"继续/接着做X"，仍是同一阶段同类活）：
1. 只读memory/index.md（扫结论定位）
2. 读TASK_STATUS.md + ISSUES.md（到哪、下一步）
3. 读该环节那一篇SOP + 上一单元样板成品

> 判不准走A还是B时，**就高走A**。

#### 2.3.4 文档同步检查清单

每次完成阶段性任务、生成新文档、或变化项目结构时，必须按`DOC_SYNC_CHECKLIST.md`检查并同步相关文档。

**同步时机**：
- 完成单个流程后
- 发现问题并解决后
- 项目结构调整后
- 大阶段完成后

#### 2.3.5 批量任务执行规范

**必须创建执行状态记录的场景**：
1. 批量处理 >3 个单元
2. 预计执行时间 >1 小时
3. 涉及多个工具链
4. 用户明确要求"批量处理"、"全部完成"

**必须立即更新TASK_STATUS.md的场景**：
1. 任务开始时（更新为"进行中"）
2. 每个子任务完成时（更新进度）
3. 任务完成时（更新为"完成"）
4. 遇到问题或阻塞时（更新问题描述）

## 三、架构设计与重构

### 3.1 重构背景

原项目名为`stock-knowledge-base`（股票知识库），结构为：
```
tools/          # 工具脚本
data/           # 数据（视频、转写稿、文章）
knowledge-base/ # 知识库成品
```

**问题**：
1. 仅针对微信生态，无法扩展到其他平台
2. 数据目录结构混乱，没有按处理阶段组织
3. 没有行业隔离，无法支持珠宝等其他行业
4. 缺少统一的平台接口和流水线编排

### 3.2 重构目标

用户提出核心需求：
> 项目不应局限于微信生态，需要抽象为多平台通用框架。每个平台有自己的采集特性，但后续处理（转写、OCR、知识提取）是公共的。同时需要行业层解耦（股票、珠宝等不同行业的知识库、文章撰写、审稿是不同的）。

### 3.3 五层架构

```
┌─────────────────────────────────────────────────┐
│  应用层 (Application)                            │
│  知识库查询 / 文稿生成 / 视频生成 / 方法提炼       │
├─────────────────────────────────────────────────┤
│  知识层 (Knowledge)                              │
│  结构化知识点 / 行业标签 / 方法笔记 (MethodNote)  │
├─────────────────────────────────────────────────┤
│  原始层 (Raw)                                    │
│  转写稿 / OCR文本 / 文章正文 / 字幕              │
├─────────────────────────────────────────────────┤
│  加工层 (Processing)                             │
│  转写 / OCR / 知识提取 / 标准化 / 方法提炼        │
├─────────────────────────────────────────────────┤
│  来源层 (Sources)                                │
│  微信公众号 / 视频号 / B站 / 抖音 / YouTube      │
└─────────────────────────────────────────────────┘
```

### 3.4 目录结构（library/00-08编号）

参考珠宝知识库项目的成熟架构，按处理阶段组织：

| 目录 | 内容 | Git入库 |
|------|------|:---:|
| `library/00_manifest/` | 采集清单、台账、水位 | ✅ |
| `library/01_video/` | 视频原始文件 | ❌ |
| `library/02_audio/` | 音频文件 | ❌ |
| `library/03_image/` | 图片文件 | ❌ |
| `library/04_transcript/` | 转写稿 | ❌ |
| `library/05_knowledge/` | 结构化知识成品 | ✅（仅stable） |
| `library/06_articles/` | 图文原文 | ❌ |
| `library/07_books/` | 书籍精华 | ❌ |
| `library/08_sources/` | 平台无关外部源 | ❌（raw/cleaned） |

### 3.5 平台插件化设计

```
platforms/
├── base.py                  # PlatformFetcher抽象基类（统一接口）
├── wechat_official/         # 微信公众号
├── wechat_channels/         # 微信视频号
├── bilibili/                # B站
├── douyin/                  # 抖音
└── youtube/                 # YouTube
```

**PlatformFetcher统一接口**（platforms/base.py）：
- `fetch_list()` — 获取内容列表
- `fetch_detail()` — 获取内容详情
- `download()` — 下载内容
- `normalize()` — 标准化为ContentItem

### 3.6 行业隔离

```
domains/
├── stock/          # 股票行业配置（标签体系、知识库模板、审稿规则）
└── jewelry/        # 珠宝行业配置
```

### 3.7 核心框架

| 模块 | 文件 | 职责 |
|------|------|------|
| 流水线编排 | `core/pipeline.py` | run_source/run_domain/run_all/incremental_update |
| 配置管理 | `core/config.py` | SourceConfig/DomainConfig/ConfigManager |
| 增量水位 | `core/watermark.py` | WatermarkManager（先成功落地再推进水位） |

### 3.8 方法提炼（MethodNote）新类型

用户补充需求：
> 看到一个抖音博主（专门做广告的），拍摄技巧、AI使用效果、内容呈现都很新颖，除了采集视频和图文，还需要分析视频的表现效果和风格，提炼出生成这个视频的方法。目的不是进入该行业，而是提炼方法，方便抄袭风格和生成视频。

**定位**：知识层的新类型MethodNote，不是新行业。

**7个分析维度**（processing/method_extraction/method_extractor.py）：
1. 拍摄技巧
2. AI工具使用
3. 内容结构
4. 视觉风格
5. 音频风格
6. 节奏控制
7. 分步生成方法

## 六、关键决策记录（ADR摘要）

### ADR-001：项目文档架构与治理规范

**决策**：建立完整的文档治理体系，参考高顿CPA项目。

**核心内容**：
- 文档分工：README给人看、AGENTS给AI看、REQUIREMENTS定义需求、WORKFLOW定义流程
- 问题驱动更新机制
- 变更影响分级（L0/L1/L2）
- 冷启动/续接双路径

### ADR-002：视频号采集的证书与代理方案

**决策**：自研Go语言MITM代理捕获工具，不依赖RES Downloader。

**关键修复**：
- 证书路径使用`os.Executable()+filepath.Dir()`，证书与二进制同目录
- 可从任意目录运行，不会生成新的未信任证书
- 支持上游代理（ClashX 7890端口），不影响全局网络

**解密原理**：DecodeKey → ISAAC64生成128KB数组 → XOR文件前128KB

### ADR-003：统一运行时工作区与过程件管理

**决策**：创建workspace/目录统一管理过程件，不入库。

**结构**：
```
workspace/
├── README.md      # 说明文档（入库）
├── logs/          # 运行日志
├── tmp/           # 临时文件
└── capture/       # 捕获数据、进度文件
```

### ADR-004：架构重构为多平台内容流水线

**决策**：从stock-knowledge-base重构为multiplatform-content-pipeline。

**7项决策**：
1. 项目改名：stock-knowledge-base → multiplatform-content-pipeline
2. 五层架构：来源层→加工层→原始层→知识层→应用层
3. library/00-08编号目录结构
4. 平台插件化：PlatformFetcher统一接口
5. 行业隔离：domains/stock/、domains/jewelry/
6. 方法提炼：MethodNote新类型（7个维度）
7. 数据分阶段迁移：先代码后数据

## 七、工程记忆体系（OKF bundle）

### 7.1 设计理念

工程记忆是跨会话的"稳定结论编译层"，解决AI模型上下文窗口限制导致的遗忘问题。

**核心原则**：
- concept只写结论与相对指针，不复制源文档正文
- 易变值（进度、计数、当天日期）不进记忆
- 冲突时以源文档为准
- AI机器初编的concept不写`verified: human`

### 7.2 现有concept

| concept | 内容 |
|---------|------|
| architecture-multiplatform-pipeline | 多平台内容流水线架构 |
| architecture-storage-layout | 四地存储分工与仓库版图 |
| architecture-tool-runtime | 工具运行目录与证书信任 |
| workflow-transcription-ocr | 视频转文字与OCR链路 |
| workflow-video-capture | 视频号采集工作流 |

### 7.3 OKF v0.2知识格式

知识库成品统一采用OKF v0.2标准档frontmatter：
```yaml
---
type: KnowledgePoint
title: 知识点标题
description: 一句话摘要
tags: [标签1, 标签2]
sources: [来源1, 来源2]
generated: process:knowledge-build
status: stable
stale_after: 2027-03-31T23:59:59+08:00
---
```

## 八、经验教训与最佳实践

### 8.1 技术层面

#### 8.1.1 证书与代理

**教训**：最初捕获工具用相对路径`ca.crt`加载证书，从项目根目录运行时会生成新的未信任证书，导致TLS握手失败、全网阻断。

**修复**：使用`os.Executable()+filepath.Dir()`，证书与二进制同目录。

**原则**：工具运行目录不影响证书加载，可从任意目录运行。

#### 8.1.2 HTTPS抓包

**教训**：尝试tcpdump/Wireshark底层抓包，发现HTTPS加密无法直接解析。

**结论**：必须用MITM代理（中间人）方式，安装自签名证书到系统钥匙串并信任。

#### 8.1.3 代理影响范围

**教训**：RES Downloader设置全局代理会影响所有程序（包括Chrome VPN、iTerm等）。

**方案**：
- 方案A：自研MITM工具，支持上游代理（ClashX 7890），只拦截微信流量
- 方案B：只设置微信的代理（需要微信支持，实际不可行）
- 最终选择方案A，影响最小化

#### 8.1.4 B站风控

**教训**：wbi签名通道遇到412风控（需登录态）。

**方案**：dynamic动态流通道免登录可用，但第一次请求可能返回空，需要有界重试。

**原则**：双通道设计，首选wbi，备用dynamic。

### 8.2 项目管理层面

#### 8.2.1 文档先行

**教训**：早期项目没有完整文档，导致对话超过50轮后AI开始遗忘规则和决策。

**方案**：建立完整的文档治理体系，重要决策一律记录到ADR，稳定结论沉淀到工程记忆。

#### 8.2.2 参考成熟项目

**教训**：从零开始设计项目架构容易走弯路。

**方案**：深度研究高顿CPA项目（治理体系）和珠宝知识库项目（数据架构），吸收成熟经验。

**原则**：不重复造轮子，站在巨人肩膀上。

#### 8.2.3 计划性评审

**教训**：项目快速迭代后积累了大量过时文档和冗余内容。

**方案**：发起计划性评审，全量精读所有MD文件，分批次改进。

**原则**：定期评审，保持文档健康度。

#### 8.2.4 变更影响分级

**教训**：批量重命名/跨目录移动如果直接执行，容易导致引用断裂。

**方案**：L1高扩散变更必须先出方案+全量影响清单，用户确认后才执行。

**原则**：拿不准就高不就低。

### 8.3 协作层面

#### 8.3.1 用户操作偏好记录

**反复强调的偏好**：
- 不要用ClashX（影响其他程序）
- 不要用内部浏览器，要用Chrome
- 不要最大化窗口
- 通过搜索找公众号/视频号最快捷
- 微信中打开公众号不能用Chrome，要用微信内置浏览器
- 不要反复搜索打开多个同名页面

**原则**：用户偏好必须记录到AGENTS.md，避免反复犯同样错误。

#### 8.3.2 阻塞时及时沟通

**教训**：微信登录、验证码等需要用户操作的场景，必须及时通知用户。

**方案**：遇到微信锁定要通知用户，用户通过手机完成解锁。
