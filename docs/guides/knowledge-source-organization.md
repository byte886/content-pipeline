# 知识源组织 SOP（采集原料 → 知识成品）

> **文档类型**：Guide（加工 SOP / 操作清单）
> **适用**：content-pipeline 中任何"把一个博主/作者/一批资料沉淀为知识成品"的任务
> **上位权威**：知识库的定位、OKF 字段与架构以 [../design/knowledge-base-organization.md](../design/knowledge-base-organization.md) 为准；**本篇只讲落地操作**（目录怎么摆、入口写什么、checklist、质检），不重复架构定义
> **配套**：采集见 [incremental-fetch.md](incremental-fetch.md)、转写见 [audio-transcription.md](audio-transcription.md)、书籍见 [books-extraction.md](books-extraction.md)；本篇管**转写/OCR 之后，知识成品怎么组织**
> **格式层**：原子知识库遵循 OKF v0.2（技能 `okf-wiki`）；本篇是 OKF 之上的"目录治理 + 入口 + 质检"约定，**不另造格式、不与 OKF 冲突**

本 SOP 回答三个问题：知识成品分几层、目录和入口怎么摆、做到什么程度算"组织好了"。目标是任何新行业/新博主都能照此一次到位，不留无入口、无台账、无状态的散目录。

---

## 一、三层解耦（原料 / 成品 / 过程件）

| 层 | 目录 | 入 git？ | 说明 |
|---|---|---|---|
| 原始资源 | `library/01_video/`、`02_audio/`、`07_books/<域>/raw/` | 否（本地/网盘） | 视频、音频、PDF、PPTX 原件 |
| 逐字转写/OCR | `library/04_transcript/`、各源 `transcripts/`、`07_books/<域>/extracted/` | 转写 md 入、原始件不入 | 自动转写初稿、OCR 文本，是**可溯源的中间层** |
| **知识成品** | **`library/05_knowledge/`** | **是** | 清洗、归并、带状态与来源的成品 |
| 过程件 | `workspace/`、台账 xlsx | 否 | 脚本、临时 json、表格台账 |

铁律：**成品引用的每个事实都能在转写/OCR 层找到出处**；不把原始大文件、明文凭证、临时票据放进 git（仓库根 `scripts/doc_health_check.py` 会拦）。

## 二、两种成品形态（先选对，再动手）

| 形态 | 何时用 | 落点 | 入口文件 |
|---|---|---|---|
| **① 博主综合文档库** | 视频量大、主题集中、需要**高密度体系结论**；愿意人工跨篇归并 | `05_knowledge/<行业>/<博主>/` | `README.md` |
| **② OKF 原子知识库** | 想先**全量可检索**、逐步精修；或来源是标准 OKF 流水线产物 | `05_knowledge/<行业>/concepts/` | `index.md`（OKF 保留名） |

两者可并存（珠宝域即如此：郭颖=①、老许=②）。**不要**对同一批视频同时维护两套重复正文；选一个为主，另一个只做导航/参照。

## 三、目录与命名

```
library/05_knowledge/
├── README.md                    # 知识层总入口（必建，登记所有行业）
└── <行业拼音或英文>/             # jewelry / stock / ceramics…（命名见仓库命名规范）
    ├── README.md                # 行业入口（≥2 个知识源时必建）
    ├── <博主名>/                # 形态①
    │   ├── README.md            # 博主源入口（必建）
    │   ├── <品类>-知识文档.md     # 综合成品
    │   ├── transcripts/         # 逐字转写（若未集中放 04_transcript）
    │   └── <台账>.xlsx           # 本地不入 git
    └── concepts/                # 形态②（OKF bundle）
        ├── index.md             # bundle 入口（必建）
        ├── videos/ articles/ books/ reports/ methods/
        └── topics/              # 跨篇主题融合页 + index.md
```

- 行业目录名用**英文/拼音**，博主名、品类成品名可保留中文（与既有库一致）。
- OKF 原子笔记文件名用**来源稳定 ID**（B站用 BV 号），不用易变的中文标题。
- 不移动、不重命名已被台账/frontmatter 引用的路径；确需迁移先全量排查引用。

## 四、入口文件写什么（模板）

**形态① 博主源 `README.md` 至少含**：
1. 一句话来源（平台、博主、采集规模）；
2. **成品文档地图**：每篇一个相对链接 + 一句摘要 + 覆盖条数；
3. 原始资源/转写/台账的存储分工（哪些入 git、哪些本地）；
4. 可信度与引用约定（draft 初稿、〔转写〕〔观点〕待补标注）；
5. 采集进度与待办（已完成/待补采，链台账与筛查报告）。
（范本：`library/05_knowledge/jewelry/珠宝学者郭颖/README.md`）

**形态② OKF bundle `index.md` 至少含**：
1. 来源、生成方式（转写工具 + okf-wiki）、生成日期；
2. 规模与成熟度（VideoNote 数、`draft/stable` 计数、topics 是否成型）——**如实说明，不把占位说成成品**；
3. 目录结构与分类导航（按 frontmatter category 现算篇数）；
4. 怎么查、怎么校验（`okf_validate.py`）、原始转写在哪。
（范本：`library/05_knowledge/jewelry/concepts/index.md`）

**行业 `README.md` 至少含**：本行业有哪些知识源、各自形态与成熟度、怎么配合/交叉验证、品类覆盖对照表。
**知识层总 `README.md`**：行业导航 + 两种形态说明 + 新增知识源登记处。

## 五、状态位与可信度（不编造）

- OKF 笔记用 frontmatter `status: draft | stable`：自动转写初稿一律 `draft`，人工核对/精修后才升 `stable`；**实质改正文后旧 `verified` 不延续**。
- 综合文档内用统一标注：**〔转写〕**＝转写存疑待核、**〔观点〕**＝博主主观看法、**待补**＝口播未展开或缺来源。
- 来源冲突不擅自覆盖，按权威度处理：**官方资料/原片 ＞ 多源互证 ＞ 高赞观点 ＞ 单一博主说法**；存疑保留并标注。
- 数字、价格、点位、专名正式引用前回看原片；时效内容（行情、价格）带时间戳。

## 六、跨篇归并原则（形态① 写综合文档时）

借鉴成熟知识库范式，要点：
1. **以品类/知识点为索引跨视频聚合**，不按视频时间线堆砌；同一主题在多视频重复讲要合并去重。
2. **一篇一个品类/主题**，篇内用 H2/H3 分小节，不跳级；过长优先篇内分节而非碎拆。
3. **Answer-First**：每小节先给结论再展开，便于 AI 检索段首命中。
4. **原子化**：一段只讲一个具体问题。
5. **MECE**：每条视频/知识点唯一归属一篇，全量可对账（用脚本 assert 覆盖条数，不重复不遗漏）。
6. **篇首上下文块**：来源（转写 X 条/原片）、覆盖范围、更新时间。
7. **交叉引用**：相关品类文档互链；表格化鉴别/分级/避坑/价格对比。
8. 早期单主题旧稿**保留不删**，内容并入综合稿并在文内注明。

## 七、新增知识源 Checklist（AI 照做）

1. [ ] 确认行业目录与知识源命名（英文/拼音行业名 + 中文博主名）。
2. [ ] 选好形态（① 综合 / ② OKF / 并存），不重复建正文。
3. [ ] 原始件入 `01/02/07`、转写入 `04` 或源 `transcripts/`、成品入 `05`，过程件入 `workspace/`。
4. [ ] 建博主源入口（README.md 或 concepts/index.md），含规模/状态/地图/存储分工。
5. [ ] ≥2 个知识源时建/更新行业 `README.md`；始终更新知识层总 `README.md` 的导航登记。
6. [ ] 标好 `draft/stable` 与可信度标注；每条事实可溯源。
7. [ ] 形态②跑 `okf_validate.py`（E=0）；全仓跑 `python3 scripts/doc_health_check.py`（不新增 ERROR/断链）。
8. [ ] 新增 docs 文档时在 `docs/DOCUMENTATION_MAP.md` 登记。
9. [ ] 更新 `project-management/active/TASK_STATUS.md` 台账，精确 `git add` 自有成品后 commit/push。

## 八、质量检查清单（交付前逐项过）

| 检查项 | 标准 |
|---|---|
| 有入口 | 知识层、行业、每个知识源都有入口文件，能从上到下点到任一成品，无死链 |
| 数量闭合 | 台账条数 = 转写条数 = 成品覆盖条数，脚本可对账，无重复/遗漏 |
| 状态诚实 | draft/stable 与实际加工深度一致；占位/原料态明确标注，不冒充成品 |
| 来源可溯 | 每篇成品 frontmatter/正文能回到转写与原片；无凭空数字 |
| 三层不混 | 原始件/凭证/过程件未入 git；成品未散落在 workspace |
| 格式一致 | 形态② 合 OKF；形态① 结构对齐既有范本；命名规范 |
| 导航登记 | 新源已在上级 README 与 DOCUMENTATION_MAP（若新增 docs）登记 |

## 九、与既有范式的关系

- **OKF（okf-wiki）**：管原子笔记/主题页的**格式与字段**（frontmatter、index/log、五信任信号、lint）。进入已有项目"只叠加格式层、不平行重建、存量不强制回填"。
- **会计知识库（accounting-kb）**：提供三层解耦、入口索引页、Answer-First、原子结构、MECE、来源优先级、结构质检清单等**治理思想**（其 CPA 课程特化的"知识点四节/题答/考季"不套用）。
- 本 SOP 是把上述两者落到 content-pipeline 的具体约定；改本 SOP 属高扩散变更，需先出方案与影响清单给用户确认。
